# 50 — Release
**Mode:** `RELEASE`
**Purpose** Promote the audited lane heads as one section release, through the release-engineer, and verify CI at the recorded merge.
**Inputs**
- PASS verdicts bound to exact `(head, tree)` pairs for every active lane.
- Lane heads and the integration head.
- `policies/ci.json`, `policies/ci-required.json`, `policies/branch-protection.json`, `policies/checks.json`, `policies/gate.json`.
- `policies/schemas/release-result.json`, `skills/release-engineer/SKILL.md`.
**Memory** Read `basemind_memory` (`list`/`search` filtered by `role:orchestrator`) at orientation; put one record at task end and whenever a seam, gotcha, or decision is found. Memory is advice, never evidence; re-run a remembered finding before citing it (`sop/00-memory.md`).

**Procedure**
1. **Gate.** Require every active lane verdict to be PASS on the same head/tree the builder reported, with no HALT for the lineage. A stale verdict is `VERDICT_STALE`; a tree difference is `TREE_MISMATCH`. Do not "re-check" by trusting prose.
2. **Freeze and enter GATE.** Record the lane heads, stop new builder dispatch for those lanes, and record the `phase: GATE`, `lane: null` dispatch for the release-engineer only after the release-train criteria in `policies/phases.json` hold (cite the policy; do not restate its numbers), plus every active lane PASS and no active lane work. Release is serialized per repository: while GATE is open no author, auditor, compliance, or crouton-alpha dispatch runs, and there is no orchestrator->hacker dispatch; the one exception is the active release-engineer spawning exactly one hacker campaign for the whole release train (`policies/phases.json#/phases/GATE/hacker_campaign_rule`, `sop/release-engineer/15-campaign.md`). No second campaign. A refused release returns to `phase: BUILD` for the bounded repair; a merged release returns to BUILD for the next section.
3. **Dispatch once.** Mint the release-engineer task context and dispatch one invocation with `task_id` and the lane heads. The release-engineer runs its whole-release-train campaign (`sop/release-engineer/15-campaign.md`) in parallel with the release checks, then follows its `release-engineer` skill: sync worktrees, reconcile `lane/a` and `lane/b` into `spec-comp`, push `spec-comp`, open or reuse the promotion PR, run exactly one watch, a PRE_MERGE release record (pinned head/tree, product-ci results, factory-gate evidence refs), then merge at the pinned head using that record's `release_record_ref`. The campaign result is folded into the record and never changes a gate predicate. The orchestrator never syncs, pushes, opens a PR, or merges.
4. **Check the release artifact.** Require the pre-merge record to be with phase PRE_MERGE and the completion record (phase MERGED) to carry `merge_sha` equal to the merge result and `merged_tree` equal to the verdict tree; the proofs are computed by the harness; release requires Proof-Root. Require the PR head to equal the pushed release head, and `guard_ref` to be present for DRAIN and null otherwise. A refusal is `RELEASE_REFUSED`; do not re-dispatch unchanged.
5. **CI is a pre-merge gate, not a post-merge guess.** Q-CHECKS is evaluated at the release head before merge: every required product-ci name is present and SUCCESS in the one `gh pr checks` run, and every factory-gate id carries a `factory check` evidence ref for that head. Proofs are computed by the harness; release requires Proof-Root. Merge only after required checks pass. A post-merge CI run on `merge_sha` is product monitoring, not a substitute for Q-CHECKS and never upgrades a pending or failed pre-merge check. `CI_PENDING` is a HOLD until `policies/ci.json.timeout_seconds`, then `CI_TIMEOUT`; a failed required check is `CI_FAILED`. A retry needs a new head, not a second merge and not a second watch. A red check opens the bounded CI-red loop: the orchestrator wakes the same release-engineer context, routes the patch to the builder, has the auditor delta the repaired head, then the release-engineer reconciles, re-heads the PR, and watches the new head once. Each loop (release-engineer↔builder, auditor↔builder) is capped at `policies/tiers.json[tier].max_cycles`; at the cap record `CYCLES_EXHAUSTED` per `policies/escalation.json` and escalate. Never lower the required set or edit a workflow to make the head green.
6. **Post-merge.** Require the MERGED completion record appended by `gh pr merge` (same evidence, real `merge_sha`/`merged_tree`), then unfreeze the lanes and continue the queue or the next section. A merged tree different from the verdict tree stops forward work.
7. **Policy drift.** If branch protection and the required set disagree, treat it as policy drift and route to `90-escalation.md`; never lower the set to make the merge pass. `.github/workflows/**` is release-engineer-owned. The builder, auditor, hacker, compliance, and crouton-alpha may not edit it, and the orchestrator does not route a workflow change as a release fix.
**Routing / handoff**
Release-engineer only. Failures return to `20`, `30`, or `40` with the exact failed predicate; human decisions go to `90`. Handoff is `task_id`, PR id, lane heads, expected tree, and the CI timeout.
**Policy refs**
`policies/release-predicates.json`, `policies/phases.json`, `policies/ci.json`, `policies/ci-required.json`, `policies/branch-protection.json`, `policies/checks.json`, `policies/tiers.json`, `policies/escalation.json`, `policies/gate.json`, `policies/schemas/release-result.json`, `agents/release-engineer.md`, `skills/release-engineer/SKILL.md`.
**Done / failure codes**
Done: `RECORD` with `reason_code: OK`; merged tree equals verdict tree and CI is green.
Failure: `HALT` or `HOLD` with `RELEASE_REFUSED`, `VERDICT_STALE`, `TREE_MISMATCH`, `CI_FAILED`, `CI_TIMEOUT`, `CI_PENDING`, or `CYCLES_EXHAUSTED`.
